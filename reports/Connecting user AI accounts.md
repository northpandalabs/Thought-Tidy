# OpenRouter leads, ChatGPT plans open, Claude subscriptions stay locked

As of November 2026, Thought Tidy has five legitimate ways to bill AI requests to a user's own OpenAI or Anthropic account. Only one of them reaches a consumer chat subscription. **OpenAI's "Sign in with ChatGPT" (SIWC) with ChatGPT plan usage** lets Go, Plus, Pro and Business subscribers spend their plan allowance in third-party apps. It is a limited preview, and paid apps like Thought Tidy go through a waitlist. It only supports a `127.0.0.1` loopback redirect, so it fits the Electron app but not the MV3 extension. **Anthropic explicitly forbids** third-party apps from offering Claude.ai login or using Free/Pro/Max/Ultra credentials on their users' behalf. Its sanctioned keyless option, **Claude Platform OAuth "Linked billing"** (beta, reportedly launched 2026-11-17), bills the user's prepaid Console API organization, never their subscription, and requires a Thought Tidy back end. That leaves **OpenRouter OAuth**, which Thought Tidy already ships, as the only mature, keyless, both-surfaces way to "connect once" and route usage to the user's own OpenAI and Anthropic billing (via OpenRouter BYOK). Direct pasted API keys remain Anthropic's stated "preferred" path, and they become much more attractive now that Claude Max/Ultra/Team plans include $100-$200 a month of API credits. Separately, **GitHub Models was fully retired on 2026-07-30**, so Thought Tidy's existing "GitHub Copilot" provider, which calls the GitHub Models endpoint, is dead and should be removed. The recommended order is: remove GitHub Models now; harden and promote OpenRouter; improve BYOK onboarding; apply for SIWC and build it desktop-first; and defer Claude linked billing to the hosted tier.

## OpenAI lets a third-party app spend a ChatGPT plan, but gates paid apps

**How it works.** SIWC plan usage is an OAuth 2.0 authorization-code flow with PKCE. On first sign-in, the app sends `client_id=dynamic_agent_client` plus an `ext_agent_host_id` and `agent_name_hint`. OpenAI's callback returns a per-user issued `client_id` that the app saves and reuses. "This direct flow needs neither a client secret nor a partner API key" ([OpenAI: Registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in)). The requested scopes are `openid profile email offline_access resource.invoke chatgpt.tokens.use.direct`, and the app must confirm `chatgpt.tokens.use.direct` was actually granted before running inference. The only documented redirect is **an HTTP loopback on `127.0.0.1`** (for example `http://127.0.0.1:1455/auth/callback`). The port may vary, but OpenAI says "Do not substitute with `localhost`" ([OpenAI: Registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in)). Access tokens last 3,600 seconds. Refresh tokens last 30 days and rotate on every refresh ([OpenAI: Token reference](https://developers.openai.com/siwc/token-sharing-open-source/token-reference)). OpenAI tells apps to keep tokens "out of browser storage" and in "protected local or self-hosted runtime storage" ([OpenAI: Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions)).

**API constraints.** Inference runs only through `POST https://api.openai.com/v1/responses`. Every request must set **`store:false` and `stream:true`**. Explicit system-role messages are rejected, so instructions go in `instructions`. `temperature`, `top_p`, `user`, `metadata`, `truncation` and `previous_response_id` (over HTTP) are not supported. Text, image and file inputs work, but hosted tools such as file search, image generation and Code Interpreter do not ([OpenAI: Preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)). `GET /v1/models` with the same token returns the models the account can use ([OpenAI: Models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference)). Thought Tidy's single-shot rewrites fit this model well. Its current Chat Completions code path does not: it uses a system role and temperature and does not stream. SIWC would therefore need a separate streaming Responses client.

**UX and branding.** OpenAI prescribes the UX in some detail. The app must show a "Continue with ChatGPT" button and a first-run "You're using your ChatGPT plan." modal. A "Using ChatGPT plan" indicator must appear near the composer or model picker, with a "Manage usage" link to chatgpt.com/settings/usage. If the app has a pricing page, it must list "Use your ChatGPT plan" for each eligible plan ([OpenAI: UI/UX guidelines](https://developers.openai.com/siwc/ui-ux-guidelines)). The guidelines expect apps to have their own subscriptions and credits and tell developers to "distinguish ChatGPT plan usage from your app's own subscription or charges." So Thought Tidy's Pro features are compatible in principle. A hotkey rewrite has no composer, so the indicator would need to live in the popup, the result overlay, or settings.

**Cost and eligibility.** The user pays nothing extra. Usage draws from the "Codex / ChatGPT work usage" already in their plan, and "connecting an app does not add a new allowance." Users can cap each app's share, and Business admins must enable each app under Tenant settings ([learn.chatgpt.com: Sign in with ChatGPT](https://learn.chatgpt.com/docs/sign-in-with-chatgpt)). On Plus, the five-hour limit is shared across every app using the plan ([OpenAI: Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions)). The plan list is **Go, Plus, Pro and Business** per learn.chatgpt.com. Launch-week coverage said Plus and Pro only ([WorkOS blog](https://workos.com/blog/sign-in-with-chatgpt-plan-usage-scope), secondary), which suggests Go and Business were added later. Free ChatGPT users are not eligible, and they are probably the majority of casual writing-tool users. Thought Tidy must handle the 403 `subscription_sharing_user_not_eligible` error and fall back gracefully ([OpenAI: Errors and recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery)).

**Which track Thought Tidy is on.** The self-serve dynamic-registration flow is documented "for open-source and locally hosted apps." Anyone "interested in offering it in a paid or remotely hosted app" is sent to an interest form ([OpenAI: ChatGPT plan usage overview](https://developers.openai.com/siwc/token-sharing-open-source)). The client-ID page says SIWC "is currently offered to a select group of commercial partners" ([OpenAI: Request a client ID](https://developers.openai.com/siwc/request-client-id)). OpenAI never defines "open-source" or "paid." But Thought Tidy is source-available rather than OSI-licensed, sells Pro features, and runs a hosted subscription, so it lands in the "paid" bucket on any ordinary reading. Nothing in the flow technically checks a license. Self-registering anyway would carry an unquantified risk that OpenAI revokes the client. The error docs also reference OpenAI confirming "deployment for your integration," which implies per-integration enablement even on the OSS track.

**Surfaces.** Electron supports SIWC cleanly. The desktop app already runs a loopback OAuth listener for OpenRouter (`desktop/lib-node/openrouter-oauth.js`) and stores secrets with `safeStorage`. A SIWC listener would bind `127.0.0.1` rather than `localhost`, and the `/v1/responses` calls would move into the main process. The MV3 extension cannot run a listener, and `launchWebAuthFlow`'s `chromiumapp.org` redirect is not a documented SIWC redirect. Storing tokens in `browser.storage.local` would also break the "out of browser storage" rule. The extension can still use SIWC by relaying through the desktop app, which already exposes a session-token-protected loopback server on `127.0.0.1:47391` for extension sync (`desktop/lib-node/sync-server.js`).

**Real-world lessons.** T3 Code is an open-source launch partner. It hit `401 token_expired` failures because it injected the one-hour access token only once, when a long-running process started ([GitHub pingdotgg/t3code #17445](https://github.com/pingdotgg/t3code/issues/17445)). Thought Tidy's short requests make mid-request expiry unlikely. The lessons that do carry over are to refresh before each request, serialize refreshes (reusing a rotated refresh token is terminal), and keep a single owner of the token set.

**Maturity and effort.** SIWC is a limited preview: announced at DevDay on 2026-09-29 per secondary coverage ([IT Brief](https://itbrief.co.uk/story/openai-launches-chatgpt-sign-in-for-16-partner-tools)), waitlisted for commercial apps, and without published numeric limits. Effort is medium to large. It needs an approval wait, a main-process OAuth module, a streaming Responses client, the required branding, an extension relay, and error-state UX.

**Other OpenAI routes, ruled out.** Three other OpenAI routes come up, and none works for Thought Tidy. First, OpenAI has no OpenRouter-style OAuth flow that mints a user-billed Platform API key. Developers are still asking for one on OpenAI's forum ([OpenAI Community](https://community.openai.com/t/feature-request-consumer-delegated-ai-access-let-third-party-apps-use-my-ai-subscription-via-oauth/1395942)), and a third-party tutorial states it plainly ([Puter tutorial](https://developer.puter.com/tutorials/openai-oauth/), secondary). That finding rests on absence of evidence, not on an OpenAI statement. Second, driving the user's installed Codex CLI through `codex app-server` with their ChatGPT login is technically easy. But OpenAI's own docs say "App-server authentication has never been permitted for commercial or hosted services" and point developers to SIWC ([OpenAI Codex docs: App Server](https://learn.chatgpt.com/docs/app-server)). Reusing Codex's OAuth client ID or its private `backend-api` endpoints is worse still; one open-source app calls that "the shakiest terms-of-service footing" ([arteeh/ki #197](https://github.com/arteeh/ki/issues/197)). Third, a ChatGPT "Plugin" (the MCP-based successor to the Apps SDK) would move the rewriting into ChatGPT itself. Plugins may sell only physical goods and must provide "functionality ... not natively supported" by ChatGPT ([OpenAI: Plugin submission guidelines](https://developers.openai.com/apps-sdk/app-submission-guidelines)). Plain rewriting is native ChatGPT functionality, and a plugin gives up the in-page hotkey.

## Anthropic sells linked billing but forbids subscription login

**The prohibition.** Anthropic's position is explicit. The current Claude Code Legal and Compliance page says subscription OAuth "is intended exclusively for purchasers of Claude Free, Pro, Max, Ultra, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications." It also says "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users," and that developers "may not collect, store, or intermediate Claude.ai credentials or session tokens" ([Claude Code Docs: Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)). The Agent SDK overview repeats this: "unless previously approved," no third party may offer "claude.ai login or rate limits for their products" ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)). That rules out a "Sign in with Claude Pro/Max" button. It also rules out reusing Claude Code's OAuth client, asking users to paste `claude setup-token` output, and reading `~/.claude/.credentials.json`. Enforcement has been real. Secondary coverage dates server-side blocking to 2026-01-09, the explicit documentation to 2026-02-19, and cutoffs of OpenClaw-style harnesses to 2026-04-04 ([WinBuzzer](https://winbuzzer.com/2026/02/19/anthropic-bans-claude-subscription-oauth-in-third-party-apps-xcxwbn/), [The Register](https://www.theregister.com/2026/02/20/anthropic_clarifies_ban_third_party_claude_access), both secondary).

**Linked billing: how it works.** The sanctioned keyless option is **Claude Platform OAuth with Linked billing**, a beta that Anthropic warns "might not be suitable for production use" ([Claude Platform Docs: OAuth overview](https://platform.claude.com/docs/en/manage-claude/oauth-apps/overview)). The user clicks "Link your Claude organization," signs in at auth.claude.com, picks an organization, optionally sets a monthly spend cap, and approves. The app's requests then carry `anthropic-beta: user-profiles-billing-2026-10-01`, an `anthropic-user-profile-id` header, and `billing_policy.bill_to: "user_profile"` on `/v1/messages` ([Claude Platform Docs: Linked billing](https://platform.claude.com/docs/en/manage-claude/oauth-apps/organization-billing-connections)). The app never receives a key. Instead, requests are signed by the app's own operator service account through **Workload Identity Federation** from AWS, Google Cloud, Entra ID or Kubernetes. That makes it **server-only**: the extension and Electron app can open the link page, but token exchange and every inference call must go through a Thought Tidy back end.

**Linked billing: limits.** Requests run in Thought Tidy's organization, so Thought Tidy's rate limits and data retention apply, and user text passes through Thought Tidy's infrastructure. On the user side, linking requires the Admin or Billing role on a directly billed Console organization. "Claude subscription plans (Pro, Max, Ultra, Team, and Enterprise) can't be linked," and Max/Ultra/Team monthly API credits cannot pay for linked usage ([Claude Help Center: Use your Claude Platform account in a third-party app](https://support.claude.com/en/articles/18467148-use-your-claude-platform-account-in-a-third-party-app)). Spend caps are per app and whole-dollar, with emails at 80% and 100%. Unlinking stops new calls within about 10 seconds. Publishing requires DNS domain verification plus an Anthropic review, unless the developer's org is invoiced. The launch date and early partners (Factory, Linear, Ramp) come only from secondary reports ([Emergent](https://emergent.sh/news/claude-linked-billing-lets-third-party-tools); [Railway blog](https://blog.railway.com/p/linked-billing-claude-platform)).

**Pasted keys are now more attractive.** Linked billing was built for Thought Tidy's hosted tier, not its client-side BYOK. It could let a hosted subscriber pay Anthropic directly instead of Thought Tidy reselling inference. Meanwhile, a 2026 change has strengthened the plain pasted-key path. Since **2026-10-07, Max ($100/mo), Ultra ($200/mo) and Team plans include monthly API credits** that go to one linked Console organization. They cover Claude API calls made with that organization's keys. They do not cover linked-billing app usage, and Free, Pro and Enterprise plans get none ([Claude Help Center: Monthly API credits](https://support.claude.com/en/articles/17154008-monthly-api-credits-for-max-ultra-and-team-plans)). So **for a Max or Ultra subscriber, pasting a key from the credit-linked org into Thought Tidy is both the compliant route and the cheapest one.** It is cheaper than linked billing, and it needs no code change, only onboarding copy. Anthropic's Help Center calls API keys "the preferred way to access Anthropic services using third-party software ... or through linked billing in apps that offer it" ([Claude Help Center: Log in](https://support.claude.com/en/articles/13189465-log-in-to-your-claude-account)). The May 2026 "Agent SDK credit" for programmatic use was paused on 2026-06-15 and never took effect ([Claude Help Center: Agent SDK with your plan](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)). The $20/$100/$200 amounts reported for it are secondary-only ([Zed blog](https://zed.dev/blog/anthropic-subscription-changes)).

**Running the user's own Claude Code (`claude -p`).** The Legal page includes a carve-out: it does not "prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription." So Thought Tidy desktop could spawn a user's logged-in `claude -p` without touching tokens. The same page, though, tells developers of "products or services" to use API keys, and the Help Center prohibits tools that "route third-party traffic against subscription limits." A paid writing tool that uses Claude Code as a text-rewrite back end fits "ordinary use of Claude Code" poorly. The practical consensus that local wrappers are tolerated rests on secondary sources: Theo's posts about T3 Code and an Anthropic staffer's reply that it was "not guidance" ([The New Stack](https://thenewstack.io/anthropic-agent-sdk-confusion/), secondary). The route is also fragile. `--bare`, which "never reads OAuth credentials," is "recommended for scripted and SDK calls, and will become the default for `-p` in a future release" ([Claude Code Docs: Headless](https://code.claude.com/docs/en/headless)). It is also slow: user reports show 2-second bare starts and 75-80-second Windows starts with tools loaded ([claudeissues #16005](https://claudeissues.com/issue/16005-claude-agent-sdk-80-second-startup-time-on-windows), secondary/anecdotal). This is a power-user curiosity, not a product feature.

**Direct browser calls.** Thought Tidy already sends `anthropic-dangerous-direct-browser-access: true` (`lib/api.js`), which Anthropic added for browser BYOK in August 2024. That fact comes from 2024 secondary coverage ([Simon Willison](https://simonwillison.net/2024/Aug/23/anthropic-dangerous-direct-browser-access)) and was not re-verified against current Anthropic docs.

## OpenRouter remains the only mature keyless bridge to both vendors' billing

**How it works.** OpenRouter's PKCE flow needs no client registration. It returns "a user-controlled API key" that is "tied to their account," and the user's requests "are billed to their own OpenRouter credits" ([OpenRouter OAuth docs](https://openrouter.ai/docs/guides/overview/auth/oauth)). Users can attach their own OpenAI and Anthropic keys once, at the account level (BYOK). If no filters are set, an attached key "is available to all models, API keys, and members" ([OpenRouter BYOK docs](https://openrouter.ai/docs/guides/overview/auth/byok)). That effectively makes OpenRouter the "central place" the question asks for. The user connects OpenAI and Anthropic billing on openrouter.ai, then signs into Thought Tidy and any other OpenRouter-enabled app with one click. One caveat: that an OAuth-issued key routes through account-level BYOK is an inference from the "all API keys" default. It is not explicitly documented for OAuth keys and should be tested.

**Cost.** BYOK on the Standard pay-as-you-go plan is free for the first **$25,000 a month of list-price inference**, then 5%. OpenRouter also charges 5.5% when users buy credits. The Free plan has no BYOK ([OpenRouter pricing](https://openrouter.ai/pricing)). At Thought Tidy volumes, routing a user's own OpenAI or Anthropic key through OpenRouter is effectively fee-free. OpenRouter does **not** link ChatGPT or Claude subscriptions. Its OAuth flow covers API billing only.

**Surfaces and maturity.** OpenRouter supports both surfaces today. Thought Tidy's extension uses `launchWebAuthFlow` with a `chromiumapp.org`/`allizom.org` redirect, and its desktop app uses a localhost loopback (`options/options.js`, `desktop/lib-node/openrouter-oauth.js`). OpenRouter documents localhost "on any port" and https callbacks; extension redirects work in practice but are not documented. The flow is mature. Two cheap improvements are available. First, `buildOpenRouterAuthUrl` in `lib/openrouter-oauth.js` sends only `key_label`, but OpenRouter accepts `limit` (a prefilled USD cap) and `expiration` (from `1-hour` to `never`), both user-editable. OpenRouter's defaults are "no credit limit and no expiry." Second, OpenRouter advises "Do not persist it in browser storage," which the extension currently does, so a default cap and expiry are the natural mitigation.

**Other user-pays brokers.** Two other user-pays brokers exist, and neither bills the user's own OpenAI or Anthropic account. **Pollinations "Bring Your Own Pollen"** offers authorization code plus PKCE, a device flow, per-key model scoping, a $5 default budget, 7-day keys with no refresh, and an opt-in **25% developer markup** ([Pollinations BYOP](https://github.com/pollinations/pollinations/blob/main/BRING_YOUR_OWN_POLLEN.md)). It bills a Pollinations balance. **Puter.js** bills a Puter account ("No API keys at all") ([Puter docs](https://docs.puter.com/user-pays-model/)). Its standard CDN-script delivery conflicts with MV3's ban on remotely hosted code ([Chrome: Remote hosted code](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code)). Both are resale models dressed as OAuth. They could replace part of the hosted subscription, but they do not answer "use my OpenAI/Anthropic account."

**Developer-side gateways.** Vercel AI Gateway, Cloudflare AI Gateway, Portkey, LiteLLM and Requesty all solve the developer's routing problem. None offers an end-user "connect your account" flow, and each would need a Thought Tidy back end ([Vercel BYOK](https://vercel.com/docs/ai-gateway/authentication-and-byok/byok); [Cloudflare BYOK](https://developers.cloudflare.com/ai-gateway/configuration/bring-your-own-keys/)). Vercel's docs contain one notable claim: "Eligible ChatGPT Pro and Business subscribers ... can claim API credits in a linked provider organization." That mirrors Anthropic's monthly credits on the OpenAI side, but no OpenAI primary page in the research confirms it, so treat it as secondary for OpenAI.

## GitHub Models died on 2026-07-30, and Google offers no subscription path

**GitHub Models.** GitHub fully retired GitHub Models on **2026-07-30**: "the playground, model catalog, inference API, and bring your own key (BYOK) are no longer available to any customer," including existing ones. Brownouts ran on 2026-07-16 and 2026-07-23, and new customers had been cut off on 2026-06-16 ([GitHub changelog 2026-07-30](https://github.blog/changelog/2026-07-30-github-models-is-now-retired/); [GitHub changelog 2026-07-01](https://github.blog/changelog/2026-07-01-github-models-is-being-fully-retired-on-july-30-2026)). The docs page now reads "GitHub Models has been retired" and notes it "was a separate service from GitHub Copilot" ([GitHub Docs](https://docs.github.com/en/github-models/use-github-models/prototyping-with-ai-models)).

**Impact on Thought Tidy.** Thought Tidy's provider labelled **"GitHub Copilot"** is in fact a GitHub Models client. `callGitHubCopilot` in `lib/api.js` posts to `https://models.inference.ai.azure.com/chat/completions` with a GitHub token and defaults to `gpt-4o`. That endpoint also appears in `manifest.json`'s host permissions and CSP `connect-src`. Every request through that provider now fails, so it is broken for any user who still has it configured, including as a fallback in `callAIWithFallback`. The label is also misleading, because the provider never used the user's Copilot subscription.

**Copilot SDK replacement.** The sanctioned successor is the **GitHub Copilot SDK**. An app signs users in with a GitHub OAuth App or GitHub App, and "Copilot usage is billed to each user's subscription." Each user needs an active Copilot subscription and is subject to their own Copilot rate limits ([GitHub Docs: Copilot SDK GitHub OAuth](https://docs.github.com/en/copilot/how-tos/copilot-sdk/setup/github-oauth)). It is a real "use the AI you already pay for" option, but it fits Thought Tidy poorly. The documented flow is a web authorization-code exchange that needs a client secret, which a source-available client cannot embed. The SDK also drives a Copilot CLI runtime, which rules out the extension. Whether Copilot's terms cover a non-coding writing tool was not established.

**Google.** Google is a dead end for subscription linking. A Google forum reply on 2026-11-16 states: "There is no official way for a third-party application to call the Gemini API using an end user's Google AI Pro or Google AI Ultra subscription quota" ([Google AI Developers Forum](https://discuss.ai.google.dev/t/question-official-way-for-a-third-party-desktop-app-to-use-a-users-google-ai-pro-ultra-subscription-with-gemini/199349)). The replier, Mahesh_Sutar, is described as Google staff, but the forum did not show a role. Gemini API OAuth bills the developer's Cloud project and is documented as a testing setup ([Gemini API OAuth quickstart](https://aistudio.google.com/docs/oauth)). Reusing Gemini CLI OAuth "is a violation of applicable terms and policies" that "may be grounds for suspension or termination," and users report 403 suspensions ([Gemini CLI ToS](https://geminicli.com/docs/resources/tos-privacy); [forum reports](https://discuss.ai.google.dev/t/urgent-mass-403-tos-bans-on-gemini-api-antigravity-for-open-source-cli-users-paid-tier/124508)). Thought Tidy's pasted Gemini key remains the only option.

**Zero-account alternatives.** Two alternatives involve no user account at all. Neither bills a user's account, but both could cut hosted costs or power a free tier. **Chrome's built-in Prompt API** has been available to extensions since Chrome 138. It needs roughly 22 GB of free disk and either more than 4 GB of VRAM or 16 GB of RAM ([Chrome: Get started with built-in AI](https://developer.chrome.com/docs/ai/get-started)). The Rewriter API was still in trial in the newest docs found ([Chrome: Built-in AI APIs](https://developer.chrome.com/docs/ai/built-in-apis)). **Windows Phi Silica**, being replaced by Aion Instruct in January 2027, can be called from Electron through a native addon on Copilot+ hardware ([MS Learn: Phi Silica](https://learn.microsoft.com/en-us/windows/ai/apis/phi-silica)).

**MCP sampling.** Letting an MCP host lend its model is not a route either. The MCP 2026-07-28 spec deprecates Sampling and recommends developers "integrate directly with LLM provider APIs instead" ([MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog.md)). Anthropic's connector help says Claude does not support sampling ([Anthropic Help Center](https://support.anthropic.com/en/articles/11503834-building-custom-connectors-via-remote-mcp-servers), search snippet only). A Thought Tidy MCP connector inside Claude or ChatGPT would be a distribution channel, not a way to power the hotkey.

## Ranked recommendation for Thought Tidy

**Fix immediately (not ranked): remove the GitHub Models provider.** Delete `callGitHubCopilot`, the `copilot` provider and its labels, the `models.inference.ai.azure.com` host permission and CSP entry, and the related tests and guide text. Show a one-time notice to users who had it configured. The provider has been non-functional since 2026-07-30, and its "GitHub Copilot" label overstated what it did.

**1. Make OpenRouter the default "connect your accounts" path (effort S).** It is the only option that is keyless, live on both surfaces, compliant, and able to route usage to the user's own OpenAI and Anthropic billing. Pass a default `limit` and `expiration` in the auth URL. Then add onboarding copy that tells users to attach their OpenAI and Anthropic keys in OpenRouter's BYOK settings once. Verify with a test account that OAuth-issued keys use BYOK.

**2. Keep and sharpen direct BYOK (effort S).** Add guided setup copy for Anthropic, aimed especially at Max/Ultra/Team users: link monthly API credits to a Console org, create a "Thought Tidy" workspace with a spend limit, and paste the key. For OpenAI, suggest a dedicated project with a budget. On desktop, move provider calls into the main process so keys never reach the renderer.

**3. Apply for SIWC now, then build it desktop-first (effort M-L).** Submit the interest form, describing Thought Tidy as a local desktop and extension app with optional paid features. Once approved, build the `127.0.0.1` loopback flow and a streaming Responses client in `desktop/lib-node/`, with the required "Using ChatGPT plan" branding. Let the extension relay through the existing desktop loopback channel. This is the only legitimate way to deliver "use my ChatGPT subscription," and Plus and Go users are the audience that most wants it.

**4. Defer Claude linked billing to the hosted tier (effort L).** Consider it only when Thought Tidy's back end is ready to take on Workload Identity Federation, Anthropic review, and the privacy cost of user text passing through its servers. Its best use is a "bring your own Anthropic billing" option for the hosted subscription. It does not help client-side BYOK, and for Max users it is costlier than a pasted key.

**5. Optional later additions.** A free on-device tier through Chrome's Prompt API, and a desktop Copilot SDK provider if a secret-holding back end ever exists.

**Do not build.** Claude subscription login or token reuse, Codex app-server or Codex OAuth reuse, Gemini or Antigravity login reuse, MCP sampling, and a subscription-backed `claude -p` bridge in a paid product.

## Conclusion

The vendors have split on the core question. OpenAI has decided that a consumer's chat subscription is portable to approved third-party apps. Anthropic has decided it is not, and offers API-billing portability instead, through monthly credits for top-tier subscribers and linked billing for server-side apps. For Thought Tidy, "connect your Claude subscription" is impossible in any compliant form. The honest pitch to Claude users is "your Max plan includes API credits; here is how to use them." For ChatGPT users, the real prize is behind a waitlist, so applying early costs little and the approval gate is the critical path.

The research also points to an architectural shift. OpenAI and OpenRouter both tell apps to keep long-lived tokens out of browser storage, and SIWC requires a loopback listener only the desktop can provide. Thought Tidy's desktop app, which already holds secrets in `safeStorage` and runs a loopback channel to the extension, is therefore the natural "central place" for account connections. The extension would become a thin client that borrows those credentials, and keep its own OpenRouter and BYOK paths only for users who do not install the desktop app.
